# 有料AIアドバイザー 設計書

作成日: 2026-08-12

`docs/requirements.md` を置き換えるものではなく、**そこに載る差分**を定義する。
両者が食い違った場合、日付の新しいこの文書が優先する。

## 1. 何を作るか

いま公開中の無料シミュレーターに、**月額課金のAIアドバイス機能**を足す。

| | 無料（現状維持） | 有料（新規） |
|---|---|---|
| ヒアリング | ポップアップ＋プルダウン（**本設計で改善**） | 同じものを使う |
| 計算 | 3シナリオ・95歳まで・枯渇年齢 | 同じ |
| **AIの助言** | なし | **診断・改善提案・再シミュレーション比較** |

- 価格: **月1,980円**
- 上限: **1ユーザーあたり月100回**
- お試し: **アカウント登録で月1回**（未登録では使えない）

### 1.1 AIの役割が当初構想から変わった

`docs/requirements.md` は「AIがヒアリングを行い、発言から項目を抽出する」設計だった。
**これを破棄する。**

理由は2つ。

1. **無料版と有料版で計算結果が1円も変わらない。** AIがやるのはフォームの代筆であり、
   同じ情報を入れれば出力は同一になる。月1,980円の対価が「入力代行」になる
2. 構造化データの収集はチャットの方が遅い（212.5秒 vs フォーム123秒、精度向上なし。
   *A Comparison of Chatbot and Form-based Data Collection*, PMC9606606）

**AIは「入力を集める」から「結果を解釈する」に移る。**
これは計算結果を入力として受け取る仕事なので、フォーム版では原理的に出せない。

## 3. 分割

**5つに分ける。それぞれ単独で意味のある状態になる。**

| # | サブプロジェクト | 完了時に出せるもの | 依存 | LLM費用 |
|---|---|---|---|---|
| **0** | ヒアリングUIのポップアップ化 | 無料機能の改善。単独でデプロイ可 | なし | 0 |
| **A** | アカウント基盤 | 登録・ログイン・ログアウト・パスワード再設定 | なし | 0 |
| **B** | Stripeサブスク | 決済して購読中になる。解約できる | A | 0 |
| **C** | AIアドバイス層 | 診断・提案・再シミュレーション比較 | B | 発生 |
| **D** | 法務・公開準備 | 規約・特商法・プライバシー・Workers Paid | C | — |

**0 は課金と完全に独立している。** 最初に着手して単独で公開できる。

**A と B は LLM を1回も呼ばない。** 課金ロジックを検証している間、API費用はゼロ。

**D が終わるまで課金を受け付けてはならない。**
特商法表記なしで日本の消費者に継続課金を販売することはできない。

## 4. サブプロジェクト0 — ヒアリングUIのポップアップ化

### 4.1 形

**ステップ式のモーダル。** 1画面につき1トピック。

⚠️ **既存の横並びフォームは廃止しない。** `docs/requirements.md` §6 は、入力を変えるたびに
即座にグラフが動くことを**「このツールの本命の体験」**と位置づけている。モーダルだけに
すると「開く→選ぶ→閉じる→見る」の往復になり、この即時性が失われる。

| 用途 | UI |
|---|---|
| **初回入力**（何を入れればいいか分からない人） | **ステップ式モーダル** |
| **微調整**（1項目いじって結果の動きを見る） | **横のフォーム**（現状維持） |

**両方が同じプルダウン部品を使う。** 増える実装はモーダルの枠とステップ進行だけで、
入力部品は共通化する。

モーダルは、保存済みのシートが無いとき（初回訪問）に自動で開く。
2回目以降は結果画面から「入力をやり直す」で開く。**開き直すと必ずステップ1から始まる。**

当初は「任意のステップに戻れる」設計にしていたが、実装時に取りやめた。
途中位置を覚えていると「入力をやり直す」を押したのに5ステップ目が出ることになり、
ボタンの文言と挙動が食い違う。個別項目の修正は横のフォームで直接できるので、
モーダルに部分編集の役割を持たせる必要がない。

モーダルを閉じた時点で `saveSheet` する。これをしないと、既定値と完全に一致する
ユーザーが1項目も変えずに完走した場合、保存が発生せず**再読み込みで再び開く。**

| Step | 内容 | 必須 |
|---|---|---|
| 1 | あなたのこと（現在年齢・職業・リタイア予定年齢） | 必須 |
| 2 | お金の流れ（世帯手取り年収・年間生活費） | 必須 |
| 3 | いまの資産（貯金・投資） | 必須 |
| 4 | 家族（子供の人数・年齢・進路） | スキップ可 |
| 5 | 老後（退職金・年金年額・受給開始年齢） | スキップ可 |
| 6 | 大きな支出（住宅購入など） | スキップ可 |

Step 1〜3 が `HearingSheet` の Tier 1、4〜6 が Tier 2 に対応する。
**Step 3 を終えた時点で計算できる。** 4以降はスキップしても結果が出る。

モーダルを閉じた後の個別項目の修正は、**横のフォームで直接行う。**

### 4.2 プルダウンの刻み

**選ぶだけで実用上の誤差が出ない粒度にする。** 帯（「400〜500万円」）は採らない。
中央値で計算することになり、年収50万円のズレが95歳まで積み上がるため。

| 項目 | 選択肢 |
|---|---|
| 現在年齢 | 18〜80 の整数 |
| リタイア予定年齢 | 45〜80 の整数 |
| 世帯手取り年収 | 100万〜3,000万円を **10万円刻み** |
| 年間生活費 | 60万〜1,200万円を **10万円刻み** |
| 貯金 / 投資 | 0〜1億円を **50万円刻み** |
| 退職金 | 0〜5,000万円を **50万円刻み** |
| 年金年額 | 0〜500万円を **5万円刻み** |
| 年金受給開始年齢 | 60〜75 の整数 |
| 子供の人数 | 「追加」「削除」ボタンで増減（上限なし） |
| 子供の年齢 | 0〜22 の整数 |
| 子供の進路 | 公立 / 私立 |
| 大型支出の金額 | 0〜1億円を **50万円刻み** |
| 大型支出のラベル | 自由入力（`<input type="text">`）。既定値は「住宅購入」 |

選択肢は最大で約300件になる。**`<select>` は300要素でも問題なく動く**ので、
凝ったコンボボックスは作らない（YAGNI）。

**人数とラベルはプルダウンにしない。** 当初は子供の人数を0〜5人のプルダウン、
大型支出のラベルを5択にする案だったが、実装時に取りやめた。
人数は追加・削除ボタンの方が行の増減として自然で、上限を設ける理由も無い。
ラベルは表示用の文字列で刻みの概念が無く、5択に押し込めると
「親の介護」のような想定外の項目を登録できなくなる。

### 4.3 既存の警告を引き継ぐ

`docs/requirements.md` §5.1.2 の「年金0円は中立な初期値ではない」警告は維持する。
Step 5 をスキップした場合、結果画面に**年金を0円として計算した旨を明示**する。

さらにプルダウン化に伴い、各ステップに「わからない場合の目安」を添える。
これは無料版の価値を直接押し上げる。

- 年金年額 → ねんきんネットへの導線
- 退職金 → 「勤続年数×相場」の考え方
- 年間生活費 → 「手取り年収 − 年間貯蓄額」で概算する方法

### 4.4 既存の「黙って間違う」ガードを必ず残す

現行の `HearingForm` には、**計算エンジンが黙って誤った結果を返す条件**を検知して
警告する仕組みが3つある。プルダウン化しても**すべて残す。**

| 条件 | 放置した場合に起きること |
|---|---|
| `retirementAge < currentAge` | `age < retirementAge` が全期間 false になり、**給与収入が全期間0円**として試算され続ける |
| `pensionStartAge < currentAge` | 入力の意図と食い違ったまま試算される |
| `customEvents[].age` が現在年齢〜95歳の範囲外 | エンジンが**黙って無視**する |

プルダウンの選択肢を動的に絞れば1つ目と2つ目は起きにくくなるが、
**`currentAge` を後から引き上げると保存済みの値が範囲外になる**ため、
選択肢を絞るだけでは塞げない。警告は必ず併置する。

### 4.5 保存

`lifeplan.sheet.v2` のまま。**スキーマは変えない**ので移行は不要。
入力経路が変わるだけで、保存する形は同一。

## 4.6 サブプロジェクト0.5 — シナリオ前提と表示単位の是正

**現状のシナリオは、比較として成立していない。** 公開中の無料機能の品質に直結し、
さらにサブプロジェクトC（AIアドバイス）はこのシナリオを読んで助言するため、
**壊れた前提の上に助言を積む前に直す。**

### 4.6.1 何が壊れているか

29歳・年収1,000万・生活費360万で試算すると、95歳時点はこうなる。

| | 表示（名目） | 今日の購買力に直すと |
|---|---|---|
| 楽観 | 32.8億円 | 約17.0億円 |
| 普通 | 7.4億円 | 約2.0億円 |
| 悲観 | -3.0億円 | 約-4,300万円 |

**問題1: 単位の違う数字を並べている。**
3つの数字はインフレ率が違うため、**それぞれ購買力の違う「円」**で書かれている。
32.8億円（1%インフレの円）と7.4億円（2%インフレの円）を直接比べることは、
**異なる単位の量を比較しているのと同じ**で、比較として成立していない。

**問題2: 悲観が「悪い未来」ではなく「破滅」になっている。**
昇給0%・インフレ3%は「実質賃金が毎年約2.9%下がり続ける」という意味。
リタイアまで36年で **`0.9709^36 = 0.345`、実質収入が現在の3分の1**になる。
生活費は実質で変わらないため、**リタイア前に収入が生活費を下回る。**
誰が試算しても破綻するので、シナリオとして情報を持たない。

**問題3: 3変数を同じ方向に同時に振っている。**
利回り・昇給・インフレを揃えて振ると67年で誤差が掛け算になる。
しかも現実には相関があり、高インフレ期は名目賃金も名目リターンも上がる傾向がある。
悲観は「インフレだけ高く、賃金もリターンも低い」という**最も起こりにくい組み合わせ**を
固定している。

### 4.6.2 実質（今日のお金）で表示する

FP実務では現在価値ベースが基本。95歳時点の名目額は意味を持たない。

**実装上の要点: 計算エンジンを書き換える必要はない。**

名目モデルの結果を `(1 + インフレ率)^経過年数` で割ると、実質モデルと
**数学的に完全に一致する。** よって**表示の境界で割るだけ**でよく、
`src/lib/lifeplan/cashflow.ts` と既存の163テストには一切触れない。

さらに重要な性質として、**枯渇年齢は割り算で変わらない。**
正の数で割っても符号は変わらないため、`depletionAge` と `temporaryShortfall` は不変。
**主指標が影響を受けない**ので、この変更のリスクは表示に限定される。

インフレ率は消えない。**退職金だけは名目固定**（§5.1.1）なので、
今日のお金に直すときにインフレ率で目減りさせる必要がある。
これは正しい挙動で、「36年後に受け取る2,000万円は今日の2,000万円ではない」
ことを可視化する。

### 4.6.3 シナリオ定数の再設定

| | 現在（名目） | 含意する実質 | **変更後（実質）** |
|---|---|---|---|
| 楽観 | 利回り5 / 昇給2 / インフレ1 | 実質+3.96 / 実質昇給+0.99 | **実質利回り5 / 実質昇給+1** |
| 普通 | 3.5 / 1 / 2 | +1.47 / -0.98 | **実質利回り3 / 実質昇給0** |
| 悲観 | 2 / 0 / 3 | -0.97 / **-2.91** | **実質利回り1 / 実質昇給-1** |

**悲観の実質昇給を -2.91% から -1% に緩める**のが本質的な修正。
-1%/年は36年で実質収入が7割になる想定で、**日本の実績に近く「悪いが起こりうる」**範囲。
-2.91%は日本が経験したどの時期よりも厳しい。

実質利回りは全世界株式の長期実績（実質5%前後）を上限に置き、
悲観の実質1%は「株式が長期でほとんど増えない」という十分に厳しい想定。

インフレ率（1 / 2 / 3%）と年金スライド（0 / 0.5 / 1.0%）は**そのまま維持する。**
前者は退職金の目減り、後者はマクロ経済スライドの表現に引き続き必要。

⚠️ 定数は「実質」で持ち、エンジンに渡す前に名目へ戻す
（名目利回り = (1+実質)×(1+インフレ)-1）。エンジンの計算仕様は変えない。

### 4.6.4 95歳時点の残高を主役から外す

現在の判定カードは「81歳で尽きる」を大きく出しており、**これは正しい設計**。
その横の「95歳時点 -3.0億円」が、意味のない桁で信頼性を削っている。

- 95歳時点の額は**補助情報として小さく**表示する
- 実質表示であることを明示する（「今日のお金で」）
- 画面下部の前提の説明を、実質ベースの表記に書き換える

### 4.6.5 やらないこと

**モンテカルロは今回やらない。** 決定論的な3シナリオは
**収益率の順序リスク**（リタイア直後に暴落が来るか）を原理的に表現できない。
同じ平均リターンでも暴落の時期次第で結果は激変する。これは本質的な限界だが、
扱うには確率的シミュレーションが必要で、サブプロジェクトC より後の検討事項とする。

## 5. サブプロジェクトA — アカウント基盤

### 5.1 方式

pre-meet と同じ。**パスワード本体をサーバーに送らない。**

1. ブラウザで PBKDF2（60万回）を回して 256bit の鍵を導出する
2. サーバーへ送るのはその鍵だけ
3. サーバーはソルト付きで SHA-256 を1回かけて D1 に保存する

サーバー側が SHA-256 の1回で足りるのは、**受け取る値が256bitの高エントロピー鍵**であり、
辞書攻撃もレインボーテーブルも成立しないため。DBが漏れても、攻撃者はパスワード候補
1つごとにブラウザ側の60万回を自分で回す必要がある。

**CPUコストがマイクロ秒オーダーに収まる**ので、Workers の 10ms 制限に余裕で入る。

保存形式は `pbkdf2c-v<kdfVersion>$<salt_b64url>$<digest_b64url>`。
`kdfVersion` を含めるのは、後で反復回数を上げたときに旧版ユーザーを判別して
移行させるため。

### 5.2 セッション

- 32バイトの乱数を Cookie に入れる（`httpOnly` / `secure` / `SameSite=Lax`）
- **D1 に保存するのはハッシュだけ。** DBが漏れてもセッションを復元できない
- 有効期間 30日

### 5.3 ヒアリングシートはサーバーに保存しない

**localStorage のまま。** 年収・資産額・家族構成を D1 に置けば、漏洩時の被害が
桁違いになる。複数端末での続きは諦める（YAGNI）。

D1 に入るのは**認証・課金・利用回数だけ**で、家計情報は入らない。
これによりプライバシー表示の変更を最小に抑えられる（§8.3）。

### 5.3.1 Cloudflare 公式のベストプラクティスからの適用（2026-08-12）

`wrangler` が導入した `workers-best-practices` スキルを読み、以下を A-2 以降に適用する。
**うち2件は A-1 で作った土台への修正を含む。**

| 項目 | 対応 |
|---|---|
| **`Env` を手書きしない** | A-1 では `worker/env.ts` を手書きした。**`wrangler types` で生成する形に切り替える**。手書きは実際の `wrangler.jsonc` のバインディングと乖離する |
| **`crypto.subtle.timingSafeEqual` を使う** | pre-meet は定数時間比較を手書きしている。**Workers には組み込みがある**（`@cloudflare/workers-types` に存在を確認済み）。⚠️ 長さが違うと例外を投げるので、**先に長さを比較**してから呼ぶ |
| **`observability` を有効にする** | 有料サービスになるため、ログとトレースは必須。`head_sampling_rate` つきで `wrangler.jsonc` に設定する |
| 秘密値の直接比較を避ける | 上記 `timingSafeEqual` で担保 |
| `Math.random()` を使わない | トークン生成は `crypto.getRandomValues()` |
| 浮いた Promise を作らない | すべて `await` / `return` / `void` / `ctx.waitUntil()` |
| `ctx` を分割代入しない | `this` が外れて実行時エラーになる |
| `as unknown as T` の二重キャスト | A-1 のレビューで既に排除済み |

#### 5.4.1 決定: signup 重複と login 失敗の応答を分ける（A-2 最終レビュー I-3）

A-2（認証コア）実装時、signup の重複メールと login の失敗を同じ応答に統一するか
どうかで判断が割れた。**最終的に次の3点を決定として残す。**

1. **signup の重複は専用の応答（409 / `EMAIL_TAKEN`）にする。** 登録済みの人に
   「パスワードが違います」と表示すると、自分が登録済みかも分からず先へ進めなくなる。
   正当な利用者が詰む害の方が、列挙で分かる情報（そのアドレスがこのサービスを

2. **login の2ケース（ユーザー不在／鍵違い）の応答統一は崩さない。** こちらは
   既存アカウントを守る側で、存在しないメールと鍵違いが区別できると有効な
   アドレスの洗い出しに直結する
3. **列挙への防御は文言ではなくレート制限である。** A-3 の Turnstile とレート制限が
   この判断の前提であり、**それが無い状態で本番公開してはいけない**

## 7. サブプロジェクトC — AIアドバイス層

### 7.1 中核となる性質

**AIは金額を一切出力しない。**

AIが返すのは「どのパラメータをどれだけ変えるか」だけで、**その結果いくらになるかは
既存の計算エンジンが出す。** 画面に出る金額はすべて163テスト通過済みのエンジンの
計算値になり、「87歳まで持ちます」とAIに書かせる経路が存在しない。

`docs/requirements.md` §3.3 が警戒した「Sonnetが金額をもっともらしく捏造する」
という最悪の故障モードが、構造的に消える。

### 7.2 AIに渡すもの

95歳×3シナリオの全210行は**送らない**。冗長でトークンを食うだけ。

1. **ヒアリングシート**（`HearingSheet` の全項目）
2. **シナリオごとの要約**
   - 枯渇年齢（`depletionAge`）と一時的資金不足の有無（`temporaryShortfall`）
   - 総資産が最小になる年齢とその額
   - 支出がピークになる年齢とその額、およびその年のイベントラベル
   - **5年刻みの総資産推移**

### 7.3 AIが返すもの（Structured Outputs）

```
{
  diagnosis:   string,                    // なぜそうなるかの説明
  key_factors: [{ label, why }],          // 効いている要因
  proposals:   [{
    label:     string,                    // 「生活費を年24万円下げる」
    rationale: string,
    changes:   [{ field, value }]         // field は enum で固定
  }]
}
```

`output_config.format` は `minimum` / `maximum` を**サポートしない**ため、
**数値の範囲検証はコード側で行う**（`docs/requirements.md` §3.2）。

### 7.4 `field` の enum — 実際に存在するレバーだけ

**計算エンジンが黒字を自動で全額投資に回すため、「積立額」というパラメータは存在しない。**
提案できるのは以下に限る。

| `field` | 対象 | 制約（サーバー側で検証） |
|---|---|---|
| `annual_living_cost` | `annualLivingCost` | 現在値の 60%〜100% |
| `household_net_income` | `householdNetIncome` | 現在値の 100%〜150% |
| `retirement_age` | `retirementAge` | 現在値〜80、かつ `currentAge` 以上 |
| `pension_start_age` | `pensionStartAge` | 60〜75 |
| `child_education_path` | `children[].path` | `public` / `private` |
| `custom_event_amount` | `customEvents[].amount` | 0〜現在値 |

**`savings` / `investments` / `retirementLumpSum` は提案対象にしない。**
本人が明日から変えられる値ではないため、助言にならない。

範囲外の `value` は**拒否して、その提案ごと捨てる**。

### 7.5 エンジンが提案を検算する

AIの提案は、そのまま表示しない。

1. `changes` を `HearingSheet` に適用したコピーを作る
2. **3シナリオすべてを再計算する**
3. **改善しなかった提案は表示しない**
   - 判定: 普通シナリオの `depletionAge` が延びる、または `null` になる、
     または `depletionAge` が同じなら `finalTotal` が増える
4. 生き残った提案だけを、元のグラフに重ねて表示する

**LLMを使いながら、出力の正しさをLLMに依存しない。**

### 7.6 前提となるエンジンの修正 — 年金の繰下げ増額

**現在のエンジンには欠陥がある。** `pensionStartAge` を遅らせると受給開始が
遅れるだけで、**年金額が増えない。**

このままだと `pension_start_age` の提案は再計算で必ず悪化し、§7.5 の
「改善しない提案は捨てる」で**常に握りつぶされる**。繰下げ受給はFPの最も標準的な
助言の1つなので、それが原理的に出せない状態になる。

**C の着手前に修正する。**

```
繰下げ（66〜75歳）: 65歳から1ヶ月遅らせるごとに +0.7%（75歳で +84%）
繰上げ（60〜64歳）: 65歳から1ヶ月早めるごとに −0.4%（60歳で −24%）
```

⚠️ **この増減率は実装時に日本年金機構の公表値で裏を取ること。**
教育費で「広く流通している値が誤りだった」事故を起こしているため、
公的な数値は必ず一次情報で確認する。

入力される `pensionAnnual` は **65歳受給開始時の額**として扱う。
Step 5 の画面にもそう明記する。

### 7.7 呼び出しの形

- **1回の生成につきAPI呼び出し1回。** 多ターンの会話にしない
- 追質問チャットは作らない（AIが自分で金額を語り始める経路になるため）
- モデル: **Claude Sonnet 5**
- `max_tokens`・モデル名は**サーバー側の定数**。クライアントから受け取らない
- 経路: Worker → AI Gateway `lifeplan` → Anthropic（BYOK、キーはWorkerに入らない）
- **SSEは使わない**（`docs/requirements.md` §3.3.2 の決定を維持）

| 出力 | 約1,500トークン ≈ $0.023 |

## 9. データモデル（D1 `lifeplan`）

既存の `nexeed-lab-db` は使わない。**専用のD1を新規作成する。**

どのテーブルがどのサブプロジェクトで入るかを1行ずつ添える。

- `users` / `sessions` / `password_resets` … サブプロジェクトA（認証の土台）
- `subscriptions` / `usage_monthly` / `processed_events` … サブプロジェクトB（課金・利用回数。
  現時点では**未実装**。存在しないのは設計どおり正しい）

```sql
-- サブプロジェクトA
CREATE TABLE users (
  id            TEXT PRIMARY KEY,
  email         TEXT NOT NULL UNIQUE,   -- 正規化済み（小文字・trim）
  password_hash TEXT NOT NULL,          -- pbkdf2c-v<n>$<salt>$<digest>
  created_at    TEXT NOT NULL
);

-- サブプロジェクトA
CREATE TABLE sessions (
  token_hash TEXT PRIMARY KEY,          -- 生トークンは保存しない
  user_id    TEXT NOT NULL REFERENCES users(id),
  expires_at TEXT NOT NULL
);
CREATE INDEX idx_sessions_user ON sessions(user_id);
-- 期限切れの一括削除で使う
CREATE INDEX idx_sessions_expires ON sessions(expires_at);

-- サブプロジェクトA（パスワード再設定）
CREATE TABLE password_resets (
  token_hash TEXT PRIMARY KEY,          -- セッションと同じく、生トークンは保存しない
  user_id    TEXT NOT NULL REFERENCES users(id),
  expires_at TEXT NOT NULL,
  used_at    TEXT                       -- 使用済みを記録する。NULL なら未使用
);
CREATE INDEX idx_password_resets_user ON password_resets(user_id);

-- サブプロジェクトB（未実装）
CREATE TABLE subscriptions (
  user_id              TEXT PRIMARY KEY REFERENCES users(id),
  stripe_customer_id   TEXT NOT NULL,
  stripe_subscription_id TEXT NOT NULL UNIQUE,
  status               TEXT NOT NULL,   -- active / past_due / canceled
  current_period_end   TEXT NOT NULL,
  updated_at           TEXT NOT NULL
);

-- サブプロジェクトB（未実装）。月100回と、お試し月1回の両方をここで数える
CREATE TABLE usage_monthly (
  user_id    TEXT NOT NULL REFERENCES users(id),
  year_month TEXT NOT NULL,             -- "2026-08"（JST基準）
  count      INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (user_id, year_month)
);

-- サブプロジェクトB（未実装）。Webhook の冪等性を担保する。処理済みイベントは二度と適用しない
CREATE TABLE processed_events (
  event_id     TEXT PRIMARY KEY,
  processed_at TEXT NOT NULL
);
```

### 9.1 利用可否の判定

`/api/chat`（アドバイス生成）は **D1 だけを見て判定する。**

```
購読中 = subscriptions 行が存在し、current_period_end > now
上限   = 購読中 ? 100 : 1        ← 未購読・期限切れは「お試し月1回」
利用可 = usage_monthly.count < 上限
```

**判定は `current_period_end` の1条件に集約する。** `status` を条件に混ぜない。

- 解約（`canceled`）しても、Stripe は `current_period_end` を当該期間の末日に保つ。
  よってこの1条件だけで「解約後も期限内は使える」が正しく表現される
- `past_due`（決済失敗・リトライ中）も同様。期限内なら使え、期限を過ぎれば止まる

`status` は**画面表示と運用のためだけに持つ**（「お支払いに失敗しています」の
案内を出す）。利用可否の判定には使わない。条件を2つに分けると、
どちらが正なのか分からなくなるため。

カウントは**生成に成功したときだけ**加算する。LLM呼び出しが失敗した回を
消費させない。加算と生成の間で落ちた場合は**消費しない側に倒す**
（利用者に不利な取りこぼしを避ける）。

年月は **JST基準**で決める。UTCで切ると日本の月初にズレる。

## 10. ルーティング

現在の `wrangler.jsonc` は**静的アセット配信のみ**（`main` なし）。ここに Worker を足す。

```
main            = Workerのエントリ
assets.binding  = Workerからアセットを返すためのバインディング
```

### 10.1 `not_found_handling` の罠（2026-08-12 に公式ドキュメントで確認済み）

**懸念は実在した。しかも「たまたま動いてしまう」ぶん質が悪い。**

`compatibility_date` が **2025-04-01 以降**だと `assets_navigation_prefers_asset_serving` が
既定で有効になり、評価順序はこうなる:

```
run_worker_first か？ → アセットに一致するか？ → Worker はあるか？ → ナビゲーションリクエストか？
```

このとき **ナビゲーションリクエストは Worker を素通りして `404.html` が返る。**
一方 `fetch()` などの非ナビゲーションリクエストは Worker に届く。

当プロジェクトの `compatibility_date` は `2026-07-01` なので**該当する。**

**なぜ危険か:** チャットやフォーム送信を `fetch()` で書いている限り動いてしまう。
しかし以下は無言で404になる。

- ユーザーが `/api/...` を直接ブラウザで開く
- `<form action="/api/...">` の素のPOST（JSを無効化された環境、フォールバック実装）
- 決済プロバイダなどからのリダイレクト着地点を `/api/` 配下に置いた場合

**対策（必須）:** `/api/*` を明示的に Worker 優先にする。

```jsonc
{
  "main": "worker/index.ts",
  "compatibility_date": "2026-07-01",
  "compatibility_flags": ["nodejs_compat"],   // stripe SDK に必要
  "assets": {
    "directory": "./out",
    "binding": "ASSETS",                      // Worker からアセットを返すのに必要
    "not_found_handling": "404-page",
    "run_worker_first": ["/api/*"]            // ← これが無いと上記が404になる
  }
}
```

`run_worker_first` は**真偽値と配列の両方**を受け付ける。`true` にすると全リクエストが
Worker を通るため、静的アセットの配信までWorkerの実行回数に計上される。
**配列で `/api/*` だけに絞ること。**

出典: <https://developers.cloudflare.com/workers/static-assets/routing/worker-script/>
および同 `/static-site-generation/`

**検証結果（2026-08-12・本番）:** `run_worker_first: ["/api/*"]` を設定した状態で、
以下の**3経路すべて**から `/api/health` が Worker に到達することを確認した。

| 経路 | 結果 |
|---|---|
| `curl`（非ナビゲーション） | `200` `{"ok":true}` `cache-control: no-store` |
| `Sec-Fetch-Mode: navigate` ＋ `Accept: text/html` を付けた `curl` | `200` `{"ok":true}` |
| **実ブラウザのアドレスバーに直接入力** | `{"ok":true}` |

**`curl` だけの確認では不十分。** curl は `Sec-Fetch-*` を送らないため
ナビゲーションリクエストとして分類されず、**設定を落としても通ってしまう。**
この設定を変更したときは、必ずナビゲーション経路も確かめること。

存在しない `/api/nope` が `404.html`（HTML）ではなく JSON のエラー本文を返すことも
本番で確認済み。これも Worker に到達している証拠になる。

### 10.2 worker/ の tsconfig は分離する（2026-08-12 実装時に判明）

**`@cloudflare/workers-types` を root の `tsconfig.json` の `compilerOptions.types` に
足してはいけない。** アンビエント型が `lib: ["dom"]` の型と衝突し、
`src/` 配下の既存コードが型エラーになる（`HTMLElement` → `HTMLSelectElement` の
キャストが通らなくなる）。`"node"` などを足しても解消しない。

**対処: `worker/tsconfig.json` を分ける。**

- `worker/tsconfig.json` … `lib` から `dom` を外し、`types: ["@cloudflare/workers-types"]`
- root の `tsconfig.json` … `exclude` に `"worker"` を追加
- `package.json` … `"typecheck": "tsc --noEmit && tsc --noEmit -p worker/tsconfig.json"`

⚠️ **`typecheck` を2構成とも走らせること。** root から除外しただけだと
`worker/` が一切検査されず、**「検査しているつもりで検査していない」**状態になる。
`worker/tsconfig.json` の `exclude` を明示的に上書きするのも必要
（親の `exclude: ["node_modules", "worker"]` を継承すると自分自身を除外してしまう）。

OpenNext は使わない。Windows を正式サポートしておらず（WSLかCIが必要）、
開発環境が Windows のため。**静的エクスポート＋Worker 1本の構成を維持する。**

比較グラフを追加したら、**必ず本番で目視する。**
