# 結果画面の固定レイアウト 設計書

**日付:** 2026-08-13
**対象:** トップページ（`/`）の試算画面と、ヒアリングのポップアップ

---

## 1. 何を作るか

1. **ポップアップを毎回開く。** 今は初回訪問（localStorage に保存が無いとき）だけ開く。
2. **基本情報を横スクロールする1本のバーにして、画面に固定する。**
3. **資産のグラフも画面に固定する。** スクロールしても消えない。

利用者の判断（2026-08-13）。目的は「入力をいじると、見えているグラフがその場で動く」を
画面のどこにいても成立させること。今は入力とグラフが縦に離れると片方が視界から消える。

**計算エンジン・保存スキーマ・`worker/` は一切変更しない。** 表示層だけの変更である。

---

## 2. この設計で覆す前提

### 2.1 PCの左右2カラムを廃止する

`Simulator.tsx:93` の `lg:grid-cols-[minmax(320px,380px)_1fr]` をやめ、
全ブレークポイントで1カラムにする。

**理由:** 380px の縦カラムの中で「横スクロール」は成立しない。
横に流すには横幅が要る。

### 2.2 フォーカストラップの先送りを撤回する

`HearingModal.tsx:80` は
**「完全なフォーカストラップは今回のスコープ外（最終レビュー指摘 C2）」**
と明記している。この判断は「モーダルは初回訪問だけ開く」ことが前提だった。

**毎回開くようにすると、モーダルは全利用者の必経路になる。**
キーボードだけで操作する人は、毎回モーダルの外へフォーカスが逃げる画面に出会う。
前提が変わったので、今回のスコープに入れる。

## 3. 調査（2026-08-13）

利用者の指示で [NameThatUI](https://namethatui.com/) を調べ、
横並びツールバーについては Baymard の実測を参照した。**設計を10か所変えた。**

| # | 分かったこと | 設計への反映 |
|---|---|---|
| 1 | **祖先に `overflow: hidden/auto/scroll` があると sticky が黙って効かない**（同サイトが「最も多い失敗」と名指し） | 実装前に祖先を監査するタスクを独立させた（→ §7.1） |
| 2 | **画面高を超える sticky は使い物にならない** | 固定領域に高さ上限を置く（→ §4.2） |
| 3 | **横並びツールバーは6〜8種類が限界**。あふれを「すべて見る」に隠すと被験者が見落とした（Baymard） | 項目は8で固定。**任意項目をバーに入れない・隠しボタンを作らない**を制約に（→ §6） |
| 4 | Baymard の「閉じた状態では選べる値が見えない」という欠点 | **今回は当たらない。** 各項目が現在値を出したままのため。対策は横あふれのみに絞る |
| 5 | **チップ＝選択・編集・削除できる対話トークン**。バッジ＝非対話 | バー内は「コンパクトなフォームフィールド」7つ＋「バッジ」1つ。**設計書から「チップ」を排除**（→ §5.1） |
| 6 | 「横に流れる操作列」に**対応する標準パターン名が無い**。近いのは Carousel（ページ送り）と Marquee（自動） | **Carousel にしない。**矢印でのページ送りを付けない（→ §5.3） |
| 7 | **`role="banner"` は告知バーの role ではなくサイトヘッダのランドマーク。**動的な助言は `role="status"` | 警告行に `role="status"` を付ける（現在は role が無い）（→ §5.4） |
| 8 | Steps は `aria-current="step"` を**1つだけ**持ち、完了段はチェックに変わる | 「ステップ 1 / 6」のテキストを本物の Steps にし、**押して直接飛べる**ようにする（→ §7.3） |
| 9 | Modal/Drawer/Sheet 共通の必須要件は**フォーカスの閉じ込めと呼び出し元への返却** | §2.2 のとおりスコープに入れる |
| 10 | ヘルパーテキストは `aria-describedby` で結ぶ部品。**プレースホルダでの代用は典型的な失敗** | バーからは外すが消さない。**毎回開くポップアップ側に残す**（→ §5.1） |

**セグメンテッドコントロールは採用しない。** 職業の4択は定義上その適用範囲だが、
4分割は `select` の約2倍の横幅を食う。**今回いちばん希少な資源は横幅**であり、
項目数が上限（8）ちょうどである以上、定石より幅を優先する。

## 4. 画面の骨組み

### 4.1 固定領域とスクロール領域

```
┌─ 固定（sticky top-0） ─────────────────────┐
│ 1. 基本情報バー（横スクロール）              │
│ 2. 警告行（不正な入力があるときだけ）        │
│ 3. 判定サマリ（1行）                        │
│ 4. 資産グラフ                               │
└────────────────────────────────────────────┘
┌─ ここから下だけ縦にスクロール ──────────────┐
│ 5. 判定の詳細（打ち手・95歳時点の残高）      │
│ 6. より詳しく（任意）                        │
│ 7. 入力をやり直す / 初期値に戻す / 保存プラン │
│ 8. 注釈                                      │
└────────────────────────────────────────────┘
```

**固定領域には不透明な背景色を敷く。** 透明のままだと、下からスクロールしてきた
文字が固定領域を透かして重なる。背景は `body` と同じ `bg-slate-50` にし、
下端に境界線を引いて固定領域の終わりが分かるようにする。

### 4.2 なぜ判定カードを全部は固定しないか

現在の `DepletionVerdict` は年金0円の警告＋判定＋3枚のカードで縦およそ300px、
グラフが360px。**合わせて固定すると縦700pxを超え、スマホでは固定領域だけで画面が埋まる。**
§3-2 のとおり、画面高を超える sticky は下端が永久に見えなくなる。

したがって:

- 固定するのは**判定を1行に圧縮したサマリ**だけ
- 判定の本文（打ち手5つ）と95歳時点の残高は**スクロール領域の先頭**に置く
- **グラフの高さを `min(360px, 40vh)` にする。** 狭い画面では縮む

`DepletionVerdict` が持つ「年金0円」の警告もスクロール領域に残す。
これは入力の不備を指す助言であって、常時見え続ける必要は無い。

## 5. 基本情報バー

### 5.1 中身

**7つのコンパクトなフォームフィールド＋1つのバッジ。** 順序は現在の `HearingForm` と同じ。

| # | 項目 | 種別 |
|---|---|---|
| 1 | 現在の年齢 | フォームフィールド |
| 2 | 職業 | フォームフィールド |
| 3 | 世帯手取り年収 | フォームフィールド |
| 4 | 年間の基本生活費 | フォームフィールド |
| 5 | 現在の貯金 | フォームフィールド |
| 6 | 現在の投資額 | フォームフィールド |
| 7 | リタイア予定年齢 | フォームフィールド |
| 8 | 年間収支（自動計算） | **バッジ**（非対話） |

**ヒント文はバーに出さない。** 「配偶者がいれば合算した額」などのヘルパーテキストは
バーの高さを倍にする。**毎回開くポップアップ側に全文が残る**ので、
利用者は少なくとも一度は必ず目にする。この変更が成立するのは、
ポップアップを毎回開くようにしたからである（片方だけを実装してはいけない）。

**ラベルは省略しない。** `SelectField` と同じく `<label for>` で結ぶ。
プレースホルダで代用しない。

### 5.2 年間収支の扱い

現在の `DerivedSummary` は `text-2xl` の金額と2行の説明文を持つパネル。
これをバッジに縮める。**マイナスのときに赤くする挙動は残す**——
「支出が収入を上回っている」という一言は説明文ごとスクロール領域へ移す。

### 5.3 横スクロールの見せ方

- 右端に**フェード**（`pointer-events-none` のグラデーション）を重ね、続きがあることを示す
- `scroll-snap-type: x proximity` で項目が半端に切れた位置で止まらないようにする
- `scroll-padding-inline` を置き、**キーボードでフォーカスを移したときに項目がフェードの下へ隠れない**ようにする
- **矢印でのページ送りを付けない。** それは Carousel であって、今回作るものではない

**PCではたいてい横スクロールは発生しない。** 8項目 × 約150px ＝ 約1200px で、
多くのPCでは収まる。横スクロールは主にスマホで効く仕組みである。

### 5.4 警告行

`isRetirementAgeInvalid` / `isPensionStartAgeInvalid` が真のとき、
バーの直下に1行の **Inline Alert** を出す。

- 該当するフォームフィールドの枠を琥珀色にする
- 警告文はバーの中ではなく**下の1行**に出す。バーの中に段落を入れると横幅が崩れる
- **`role="status"` を付ける。** 値を変えるたびに読み上げが割り込む `role="alert"` は使わない
- **`role="banner"` は使わない。** これはサイトヘッダのランドマークである

年金の受給開始年齢は任意項目としてスクロール領域に置くが、
**警告だけは固定領域に出す。** 試算が黙って間違っている状態を、
スクロールしないと気づけない場所に置いてはいけない。

### 5.5 `overflow-x` の副作用

`overflow-x: auto` を指定すると、CSS の規定により `overflow-y` は `visible` のままではいられず
`auto` に計算される。つまりバーは縦方向にもスクロールコンテナになり、
**フォーカスリングが上下で切れうる。** 内側に縦パディングを確保して逃がす。

## 6. スクロール領域

現在の `HearingForm` から基本情報セクション（Tier 1）を取り除き、
「より詳しく（任意）」だけを残す。**中身は変えない。**

- 退職金 / 年金の年額 / 年金の受給開始年齢
- 子供（追加・削除）
- 大きな支出の予定（追加・削除）

**この5つを絶対にバーへ入れない。** 子供と支出は行が増減するので横一列に収まらないうえ、
入れれば項目数が §3-3 の上限（6〜8）を超える。
**あふれた項目を「もっと見る」ボタンに隠すこともしない。**Baymard の被験者はそれを丸ごと見落とした。

## 7. ポップアップ

### 7.1 毎回開く

`Simulator.tsx:32-44` の「保存が無いとき」という条件を外し、マウント時に必ず開く。
**保存の復元は今までどおり先に行う**ので、2回目以降は入力済みの状態で始まる。

### 7.2 抜け道を2つ用意する

毎回開く以上、再訪者が「年収だけ直したい」ときの経路が要る。

1. **クリックできる Steps**（§7.3）。目的のステップへ直接飛ぶ
2. **「この内容で見る」ボタン**。全ステップのフッターに置き、押せば即座に閉じる

✕ と Escape は今までどおり残す。

### 7.3 Steps

「ステップ 1 / 6」というテキストを、本物の Steps に置き換える。

- 段は6つ。ラベルは既存の `STEP_TITLES` をそのまま使う
- **`aria-current="step"` は現在の段だけに付ける。** 2つ以上に付けると読み上げ位置が壊れる
- 完了した段は番号をチェックに替える
- **各段は押せる。** 押すとその段へ移動する
- 状態は `step` という単一の数値から導出する。完了・現在・未到達を別々に持たない

### 7.4 フォーカストラップ

- 開いたらモーダル内の最初の操作要素へフォーカスを移す（既存の挙動）
- **Tab / Shift+Tab がモーダル内で循環する**
- **閉じたら、開く直前にフォーカスがあった要素へ返す**
- Escape で閉じる（既存の挙動）

背景の暗い層は **scrim** と呼ぶ。既存の `bg-slate-900/50` がそれにあたる。

## 10. テスト

### 10.1 新しく担保すること

1. **保存済みデータがあってもポップアップが開く**（現在は逆をテストしている可能性が高い。反転する）
2. バーの項目を変えると再計算が走る
3. リタイア予定年齢が不正なとき、バーの下に `role="status"` の警告行が出る
4. 任意項目（子供・大きな支出）はバーではなくスクロール領域に描画される
5. Steps の段を押すとその段へ移動する
6. `aria-current="step"` が付いている要素はちょうど1つ
7. モーダル内で Tab が循環し、閉じると呼び出し元へフォーカスが返る
8. 「この内容で見る」を押すとモーダルが閉じる

### 10.2 書き換えが必要な既存テスト

`HearingForm.test.tsx`（→ `OptionalDetailsForm.test.tsx`）・`Simulator.test.tsx`・
`HearingModal.test.tsx`。項目の移動とモーダルの開閉条件の変更に伴うもの。

### 10.3 テストしないこと

**固定されているかどうか（sticky）は jsdom では検証できない。**
CSSクラスの有無を見るテストは実装の写経になるだけなので書かない。
**本番デプロイ後に実機で目視する。**

設計書 §11「比較グラフを追加したら必ず本番で目視する」に前例がある
（lint・コードレビューを通過したまま本番でY軸が-5億円まで伸びていた）。同じ扱いにする。

目視する項目:

| 対象 | 期待 |
|---|---|
| PC・スマホでスクロール | バーとグラフが画面に残り続ける |
| スマホでバーを横に払う | 8項目すべてに到達できる |
| 固定領域の高さ | 画面高を超えない（下端が切れない） |
| リタイア年齢を不正にする | 警告行が固定領域に出る |
| キーボードだけで操作 | バーの項目がフェードの下に隠れない。モーダルからフォーカスが逃げない |

## 11. 意図的にやらないこと

- **計算エンジン・保存スキーマ・`worker/` を触らない。** 表示層だけの変更である
- **職業をセグメンテッドコントロールにしない**（§3）。横幅を優先する
- **スマホでボトムシートにしない。** ポップアップは中央のモーダルのままにする。
  ブレークポイントごとに提示方法を変えると、フォーカス管理を2通り持つことになる
- **矢印でページ送りするCarouselにしない**（§5.3）
- **バーの項目を折りたたむ「もっと見る」を作らない**（§6）
- **`DepletionVerdict` の中身（打ち手5つ・3シナリオのカード）を削らない。**
  置き場所を固定領域からスクロール領域へ移すだけ

## 12. 未確定事項

| 項目 | 状態 |
|---|---|
| バーの1項目あたりの幅 | 実装時に実機で決める。8項目が1200px前後に収まることが目安 |
| グラフの高さの下限 | `40vh` が横向きスマホで潰れすぎないか、実機で確認する |
| 固定領域の `z-index` | ポップアップ（`z-50`）より下、それ以外より上。実装時に既存の指定と突き合わせる |
