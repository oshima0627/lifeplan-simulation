# ライフプランシミュレーター 要件定義

FPが相談者にヒアリングしながらライフプランを作っていく体験を、AIとの対話で再現するWebサイト。
年齢・家族構成・収支・ライフイベントを対話で聞き取り、**将来の資産推移（キャッシュフロー表）を3シナリオで可視化**する。

- 作成日: 2026-08-10
- 公開範囲: 一般公開（ログイン不要）

---

## 1. このツールが答えるもの

**「このままいくと、資産は何歳で尽きるのか」** — これが唯一の中心的な問い。

グラフはその答えを示すための手段であり、付属情報ではない。楽観・普通・悲観の3シナリオを重ねて描き、**悲観シナリオでも破綻しないなら、その計画は強い**と判定できる状態を作る。

### 設計思想の出典

ライフプラン作成の手順・前提の置き方・3シナリオの考え方は、リベラルアーツ大学（両学長）のライフプラン論に準拠する。要点は以下。

- ライフプランは「将来を当てる」ものではなく **「今、何を選べるかを知る」** ためのもの
- 資産残高 = 前年残高 ×(1+運用利回り) ＋ 当年収支
- 前提は楽観値を使わない。**インフレ率を必ず置く**
- 寿命は長めに置く（「足りなくなる年」を先に見つけるのが目的）
- 打ち手は5つしかない：生活費を下げる／収入を増やす／利回り・期間を見直す／想定外の支出を防ぐ／支出の優先順位を見直す

参照: `projects/libecity-library/docs/11_lifeplan.md`

### スコープ外（意図的に入れないもの）

| 除外するもの | 理由 |
|---|---|
| 株式/債券の資産配分（アセットアロケーション） | 別の関心事。本ツールは資産の**総額推移**のみを扱う |
| 生活防衛資金の算出 | 上と同じ。配分の話に踏み込むとツールの焦点がぼける |
| 個別商品の推奨 | 中立性を損なう。「作った人の目的を疑え」の対象になる |
| 価値観マップ作成支援 | 本来はライフプランの前段だが、別ツールの領域 |
| URLパラメータでの条件共有 | 項目数が多くURLが破綻する。localStorage保存で代替 |

## 2. アーキテクチャ

```
[ブラウザ]  静的エクスポートされた Next.js
  ├─ チャットペイン ─┐
  └─ ライブフォーム   │  （ヒアリングシートの状態を保持）
                      │
                      ↓ POST /api/chat （1ターン = 1リクエスト）
[Cloudflare Worker]  ← 唯一のサーバーコード
  ├─ Turnstile 検証
  ├─ Durable Object で 1日あたりの回数制限
  ├─ サーバー側ステートマシン（未入力項目の判定）
  └─ fetch → Cloudflare AI Gateway → Claude API (Sonnet 5, SSE素通し)
                                      ↑ Budget Limitノードで金額上限
[ブラウザ]
  └─ 計算エンジン（純粋関数・クライアント実行・テスト必須）
       ヒアリングシート → 年次キャッシュフロー × 3シナリオ → グラフ
```

### 主要な選択と理由

| 選択 | 理由 |
|---|---|
| **OpenNextによるSSRを使わない**（静的エクスポート＋Worker 1本） | サーバーが必要なのは`/api/chat`だけ。静的アセットはCloudflareで無料・無制限、Workerバンドルは数十KBに収まる。OpenNextはWindowsを正式サポートしておらず（WSLかCIが必要）、本プロジェクトの開発環境はWindows |
| **計算エンジンはクライアント実行** | 純粋関数でサーバーに置く理由がない。Workerバンドルも小さく保てる |
| **Cloudflare Workers** | `fetch()`の待ち時間はCPU時間に計上されず、クライアント接続中は実行時間の上限なし。90秒のLLM生成でもCPU数msしか消費しない。待ち時間も課金されるLambda系より圧倒的に有利 |
| **APIキーをWorkerに置かない**（AI Gateway BYOK） | Cloudflare Secrets Store側に保管し、WorkerはGatewayトークンのみ保持。ローテーションが再デプロイ不要になり、同時にBudget Limitノードが使える |

> ⚠️ **Cloudflare Workers の Freeプランは使えない。** CPU 10ms上限では足りず、$5/月のPaidプランが前提。

## 3. ヒアリングの仕組み

### 3.1 役割分担

**LLMは会話文の生成と情報抽出だけを担当し、「何が未入力か」は一切管理しない。**

| 担当 | 責務 |
|---|---|
| サーバー側ステートマシン | ヒアリングシートの正（source of truth）。未入力項目の判定、Tier遷移、バリデーション |
| LLM (Claude Sonnet 5) | 直前のターンからの情報抽出と、次の質問文の生成 |

この分離は必須。多ターン会話ではLLMは序盤に立てた前提に固執し、道を誤ると回復しない性質が知られている（*LLMs Get Lost In Multi-Turn Conversation*, arXiv:2505.06120, ICLR 2026 Outstanding Paper — 情報を1ターンずつ小出しにする設定で全モデルが平均39%性能低下、その内訳は能力低下ではなく**信頼性の著しい低下**）。**LLMに毎ターン「今回のターンの内容だけ」を担当させれば、20ターン先で文脈を見失っても影響しない。**

### 3.2 API呼び出しの形

**Structured Outputs（`output_config.format`）を使い、1ターン1回の呼び出しで会話文と抽出結果を同時に得る。**

```
{
  reply_to_user:    string,   // ユーザーに表示する会話文
  extracted_fields: { ... },  // 今回のターンから抽出できた項目
}
```

`record_field` のようなツールを毎ターン呼ばせる方式は採らない。ツール呼び出しは1往復増えるだけで、制約付きデコードによる形式保証は Structured Outputs でも同じ。またこのパターンはAnthropicのドキュメントに記載がなく、推奨された手法ではない。

> ⚠️ `output_config.format` は JSON Schema の `minimum`/`maximum`/`minLength`/`maxLength` を**サポートしない**。数値の範囲検証はコード側で行う。

### 3.3 Sonnet 5 を使うための補償策

Anthropicのドキュメントに明記がある通り、**必須パラメータが不足しているとき、Sonnetは「もっともらしい値を推測して埋めてしまう」ことがある**（Opusは「足りない」と認識して聞き返す傾向が強い）。金額計算エンジンに渡す入力では、これはエラーではなく**自信満々の誤った数字**を生む最悪の故障モードになる。コスト優先でSonnet 5を選択したため、以下で補償する。

1. **enumで縛れる項目はすべてenumにする。** `雇用形態: "会社員"|"公務員"|"自営業"|"その他"` のようにスキーマで選択肢を固定すれば、架空の値を生成できない（`type: string` だと生成できてしまう）
2. **各抽出項目に `confidence` を持たせる。** 「ユーザーが明言した値」か「推測」かをLLM自身に申告させ、推測フラグが立った項目はフォーム上で色を変えて必ず確認を促す
3. **会話終了時に照合パスを1回走らせる。** 会話全体を見直して抽出結果を再検証し、蓄積された状態と食い違う項目は上書きせず確認プロンプトとして提示する

### 3.4 状態の注入方法

現在のフォーム状態は、**各ユーザーターンの末尾に `<state>` ブロックとして追記**する。

- mid-conversation system message（`{"role": "system"}` を `messages` に追加する方式）は **Sonnet 5 では400エラー**になるため使えない（Opus 5 では利用可）
- **履歴は追記のみ**とし、過去のターンの `<state>` ブロックは書き換えない。これによりプロンプトキャッシュのプレフィックスが不変になり、キャッシュが完全に効く
- ユーザーの自由入力に含まれる `<state>` 風の文字列は、**注入前にサーバー側でエスケープする**（ユーザー入力は偽装可能なため）

### 3.5 プロンプトキャッシュ

- top-level `cache_control` に **`ttl: "1h"`** を指定する。デフォルトの5分TTLは人間のペースの対話に短すぎ、ユーザーが席を外すと全履歴を再び満額で支払うことになる
- **`tools` とスキーマは会話の途中で変更しない**（変更するとキャッシュが全損する）
- `usage.cache_read_input_tokens` を監視し、0が続く場合はプレフィックスに変動要因がある

## 4. ヒアリングシート（データモデル）

計算に必要な項目を2階層に分ける。これがステートマシンの中身であり、チャットの進行順序を決める。

### Tier 1 — 必須（これが揃わないと計算できない）

| 項目 | 型 | 備考 |
|---|---|---|
| 現在の年齢 | number | |
| 職業 | enum | 会社員／公務員／自営業／その他 |
| 世帯手取り年収 | number | 配偶者がいれば合算 |
| 年間の基本生活費 | number | 「月いくら」で聞いて×12 |
| 現在の貯金 | number | 利回り0%で保有する現金 |
| 現在の投資額 | number | 利回りが適用される資産 |
| リタイア予定年齢 | number | |

> **毎月の積立額は入力項目にしない。** キャッシュフロー表では収支（＝収入−支出）が積立額そのものであり、3つすべてを入力させると数字が整合しない。代わりに**導出された年間収支をフォーム上に表示**し、ユーザーが「思っていた積立額と合っているか」を検算できるようにする。乖離が大きければ生活費の申告が実態とずれている合図になる。
>
> **貯金と投資を分けるのは必須。** 1本にまとめると貯金まで年5%で増えることになり、資産推移を構造的に過大評価する。これは出典が「危険サイン」として挙げる**楽観シナリオしかない状態**を、ツール自身が作り出してしまう。

### Tier 2 — 精度向上（デフォルト値あり・スキップ可）

| 項目 | 型 | デフォルト |
|---|---|---|
| 配偶者の有無・年齢 | — | 無 |
| 子供（人数・現在年齢・進路） | array | 無 ／ 進路は公立 |
| 昇給率 | number | シナリオ側で設定 |
| 退職金 | number | 0 |
| 年金見込額・受給開始年齢 | number | 0 ／ 65歳 |
| 住宅（購入予定 or 賃貸継続） | — | 現状維持 |
| その他ライフイベント | array | 無 |

### 進行ロジック

```
Tier 1 に未入力あり  → 質問を続ける（終了させない）
Tier 1 が充足        → 「一度計算できます。もう少し精度を上げますか？」と提案
Tier 2 も充足 or スキップ → 確認画面へ
```

**この分岐はコード側で制御する。** LLMは会話文の生成と抽出だけを担当する。

### 教育費の自動生成

子供を入力すると、現在年齢から進学年（小・中・高・大）を逆算し、進路に応じた金額をその年の支出イベントとして自動生成する。

## 5. 計算エンジン

UI非依存の純粋関数。ユニットテスト必須。

### 5.1 年次ループ

```
現在年齢 から 95歳 まで 1年刻みで:
  n = 経過年数

  収入 = 給与（n < リタイアまでの年数 ? 年収 × (1 + 昇給率)^n : 0）
       + 年金（年齢 ≥ 受給開始年齢）
       + 退職金（リタイアした年のみ）

  支出 = 基本生活費 × (1 + インフレ率)^n
       + ライフイベント費（その年に発生する分）

  収支 = 収入 − 支出

  投資 = 前年投資 × (1 + 利回り)
  貯金 = 前年貯金

  収支 ≥ 0 の年 → 投資 += 収支          （余剰は投資に回す）
  収支 < 0 の年 → 貯金 += 収支          （不足はまず貯金を取り崩す）
                  貯金 < 0 なら 投資 += 貯金, 貯金 = 0   （足りなければ投資を取り崩す）

  残高 = 貯金 + 投資
```

**貯金には利回りを適用しない。** 貯金と投資を1本にまとめて全額に利回りを掛けると、資産推移を構造的に過大評価する。取り崩しは貯金を先に減らし、尽きたら投資に手を付ける順序とする。

**寿命は95歳固定**とし、入力項目にしない。「足りなくなる年を先に見つける」ことが目的なので長めに置くのが定石であり、ユーザーに寿命を入力させる体験的コストに見合わない。

**インフレ率は支出に、利回りは投資に適用する**（名目利回り）。実質利回りに換算する方式は採らない。

### 5.2 3シナリオ

利回りだけでなく3変数を連動させる。

| | 利回り | 昇給率 | インフレ率 |
|---|---|---|---|
| 楽観 | 5% | 2% | 1% |
| 普通 | 3.5% | 1% | 2% |
| 悲観 | 2% | 0% | 3% |

### 5.3 出力

1. **年次グラフ** — 3本の推移線を重ねて表示
2. **「資産が尽きる年」の判定** — 各シナリオで残高が初めてマイナスになる年齢。悲観シナリオでも尽きなければ「その計画は強い」

**判定はグラフの付属情報ではなく主役として表示する。**

## 6. 画面構成

1画面完結。左にチャット、右にライブフォーム。モバイルではフォームを上部に畳み、進捗バーのみ常時表示、タップで展開。

```
[ヒアリング] ──→ [確認・修正] ──→ [グラフ]
     ↑                                 │
     └──── 項目クリックで即修正・即再計算 ────┘
```

### ライブフォームを併置する理由

チャット単体には実証的な弱点がある。査読済みの直接比較（chatbot vs Webフォーム, n=206）で、チャットは**中央値212.5秒 vs フォーム123秒 ＝ 約73%遅い**。主観的な好みはチャットが勝つ（69.9%）が、**ユーザビリティ(SUS)に有意差はなく、データ精度は測定されていない**（PMC9606606）。多段階で順序に依存し、誤りのコストが高いタスクほどチャットは不利になり、ユーザーは過去の決定を再構成するためにログを遡ることになる。

併置フォームはこれを直接潰す。**フォームが正であり、チャットは入力手段の一つ**という位置づけにする。

- 抽出結果はリアルタイムでフォームに反映される
- **各項目はクリックで直接修正できる**（修正にLLMを経由させない）
- 進捗は n/m 形式で表示（ステートマシンが算出。LLMに言わせない）
- **導出値（年間収支 ＝ 手取り年収 − 基本生活費）を表示する。** ユーザーが自分の感覚と照合でき、乖離があれば生活費の申告ずれに気付ける
- **計算エンジンに渡す前に、全項目の確認画面を必ず挟む**

グラフ表示後もフォームは残し、どの項目をいじると「資産が尽きる年」がどう動くかをその場で試せるようにする。**ライフプラン表の価値は「作ること」ではなく「打ち手を当てはめて再計算すること」にある。**

### 保存

入力内容は **localStorage に保存**する。ライフプランは年1回見直す前提のツールであり、毎回ゼロから聞き直すのは体験として成立しない。

### プライバシー表示（必須）

年齢・年収・家族構成・資産額という機微な情報を扱い、かつ**会話内容はClaude APIに送信される**。開始前に以下を明示する。

- 入力データはブラウザに保存され、当サイトのサーバーには保存されない
- **ヒアリングの会話内容はAnthropic社のAPIに送信される**

ここを曖昧にすると、「作った人の目的を疑え」という原則の対象に自分自身がなる。

## 7. コスト・不正対策

一般公開する以上、これは付帯機能ではなく**公開の前提条件**。ログイン不要のClaudeプロキシは、実質「レート制限付きでAPIキーを公開している」のと同じ。

| 層 | 手段 | 効果 |
|---|---|---|
| **金額** | **AI Gateway の Budget Limit ノード** | **唯一の確実な上限。他の層がすべて破られても請求は止まる。公開前に必ず設定する** |
| ボット | Turnstile（無料） | サーバー側で検証してからClaude呼び出し |
| 頻度 | WAFレート制限 ＋ Durable Object で 1日N回/IP | エッジで弾く分はWorker課金も発生しない |
| 1回あたり | `max_tokens`・履歴長・モデル名を**すべてサーバー側で固定** | クライアントから受け取らない |
| 事故時 | このプロジェクト専用のAnthropic APIキー | 漏洩時の被害を隔離 |

> ⚠️ **Workers のレート制限バインディングはコロケーション単位**（グローバルではない）。攻撃者がPoPを跨ぐと実効クォータが倍増するため、これ単独をコスト上限として使わない。

### シークレット管理

- **AI Gateway BYOK** を第一選択とする。ANTHROPIC_API_KEY は Cloudflare Secrets Store に保管し、Workerには入らない
- `wrangler.jsonc` の `vars` には**絶対に置かない**（平文でダッシュボードから見える）
- `NEXT_PUBLIC_*` という名前を付けない（ビルド時にクライアントバンドルへ埋め込まれる）

## 8. テスト戦略

| 対象 | 方法 |
|---|---|
| 計算エンジン | Vitestユニットテスト。境界値（資産が尽きる年、リタイア年、年金受給開始年）、教育費イベントの発生年、3シナリオの分岐を網羅 |
| ステートマシン | ユニットテスト。未入力判定、Tier 1→2の遷移、バリデーション |
| LLM抽出 | ゴールデンテスト（会話サンプル → 期待される抽出結果）。**LLMは非決定的なのでCIの必須ゲートにはせず**、プロンプト変更時に手動実行する回帰チェックとして運用 |
| ストリーミング | **本番デプロイに対して早期に実機確認。** SSEは`next dev`で動いて本番で止まる典型パターンがあるため、机上検証で済ませない |

### SSE実装の注意

- **上流のボディをそのまま素通しする**（`return new Response(upstream.body, { headers })`）。SSEフレームをJSでパースして再エンコードするとトークンごとにCPUを消費する
- `Cache-Control: no-cache` / `Content-Encoding: identity` / `X-Accel-Buffering: no` を付与する
- クライアント切断を `AbortSignal` で上流fetchに伝播させる（切断後もトークン課金が続くのを防ぐ）
